What it is

sahinit is the binary of sash-init, a Go service supervisor intended to replace systemd as PID 1. Units are strict JSON. It boots them in dependency waves with readiness checks and bounded restarts (with an optional backoff delay, and restart_limit after repeated crashes), runs each under an explicit numeric identity with a clean environment, can confine it with Landlock, puts each service in its own cgroup v2 cgroup with kill-all and memory, CPU and PID limits, and answers on a local control socket that refuses requests from the services themselves. In strict boot (PID 1) every boot unit is essential unless it says "essential": false, so a failed essential unit sends the host to recovery. A notify unit can have a watchdog, and sahinit host notify-adapter wraps a program that speaks sd_notify. supervise --log-dir keeps a bounded on-disk journal that sahinit logs and sahinit events read. A candidate catalog can be checked with sahinit validate and, through the control socket, compared and applied live (diff, apply, rollback; root only), and explain says why a unit is not running. A signed, verified deployment with immutable generations is the one mode where a signed policy admits units. A unit can also name a sash service script: sahinit verifies the script's signed grant before every start and performs its privileged steps itself. sahinit migrate previews conversion from systemd, daemontools and OpenRC. sahinit policy verifies and caches signed boot-policy metadata.

Current scope. sahinit supervise under an existing init with a delegated cgroup is the supported mode. PID 1 mode is experimental: it is tested in QEMU boots (initramfs images, and a disposable ext4 disk booted twice), not on real hosts. Boot policy is metadata only for --dir catalogs: it is verified and cached, and nothing admits or refuses a unit because of it. A verified deployment (--deployment-root, exec units only) is the one mode where a signed policy admits units, and it has no issuer yet. sash services run with test-made grants and floors; there is no fleet signer and no policy issuer yet. Sandboxed units cannot hold capabilities, and the network is not confined. There are no packaged releases. This guide describes the branch feat/host-ops, which is not yet merged into main. sahinit is licensed GPL-3.0-or-later (see License).

Quick start

Build from source (Go 1.26), write one unit, check the plan and run the supervisor under your current init. On Linux supervise needs a delegated cgroup v2; for a first try without one, add --no-cgroups.

git clone https://github.com/afterdarksys/sash-init.git
cd sash-init && git checkout feat/host-ops
./build.sh
go build -o /tmp/sahinit ./cmd/sahinit

sudo install -d -o root -g root -m 755 /etc/sahinit/units
sudo tee /etc/sahinit/units/hello.json >/dev/null <<'EOF'
{ "name": "hello", "exec": ["/bin/sleep", "3600"], "type": "simple", "ready": "exec",
  "execution": { "uid": 65534, "gid": 65534 } }
EOF
sudo install -d -m 700 /run/sahinit

sudo /tmp/sahinit plan --dir /etc/sahinit/units
sudo /tmp/sahinit supervise --dir /etc/sahinit/units --socket /run/sahinit/sahinit.sock --no-cgroups &
sudo /tmp/sahinit ctl --socket /run/sahinit/sahinit.sock status hello

plan prints one boot wave per line and names every refused or cgroup-trusted unit on stderr. ctl prints the JSON response and exits 0 when it says "ok":true.

Operations guide

How to install, boot, configure, upgrade, roll back, recover and troubleshoot sahinit. Flags are in cli, unit fields in units, files in config files and tokens in codes.

Scope today. supervise is the supported way to run sahinit: under an existing init with a delegated cgroup v2. PID 1 mode is experimental: it is exercised in QEMU boots (initramfs images, and a disposable ext4 disk booted twice), not on real hosts. Boot policy is metadata only for --dir catalogs: nothing admits or blocks a unit from it. A deployment (--deployment-root) is the one place a signed policy admits units; there is no issuer for it yet. sash services run with test-made grants and floors; there is no fleet signer yet.

The VM suite runs Debian's Linux 6.1 amd64 kernel; the Docker suite runs whatever kernel the Docker host has.

Install

sahinit is one static Go binary. There is no package or release download yet; build from the repository (Go 1.26):

git clone https://github.com/afterdarksys/sash-init.git
cd sash-init
./build.sh                                  # tests, vet, Linux cross-compile
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o sahinit ./cmd/sahinit
install -o root -g root -m 755 sahinit /usr/local/sbin/sahinit
install -d -o root -g root -m 755 /etc/sahinit /etc/sahinit/units

The binary, every directory above it, the unit directory and every unit file must be owned by root (or the supervisor's uid) and not group- or other-writable. Check a catalog before running it:

sahinit plan --dir /etc/sahinit/units

plan prints the boot waves and names every refused or cgroup-trusted unit.

Running under another init (supervise)

systemd

# /etc/systemd/system/sahinit.service
[Unit]
Description=sahinit service supervisor

[Service]
ExecStart=/usr/local/sbin/sahinit supervise --dir /etc/sahinit/units --socket /run/sahinit/sahinit.sock
ExecReload=/usr/local/sbin/sahinit ctl --socket /run/sahinit/sahinit.sock status
Delegate=yes
RuntimeDirectory=sahinit
RuntimeDirectoryMode=0700
KillMode=mixed
TimeoutStopSec=11min

[Install]
WantedBy=multi-user.target
  • Delegate=yes makes the unit's cgroup writable by sahinit, which becomes the cgroup root: it moves itself into ROOT/supervisor and creates ROOT/NAME.service per service. systemd's ExecReload runs in ROOT/.control, which sahinit accepts as a control peer while the root is protected (a controller enabled below it).
  • The socket directory must be writable only by its owner; /tmp is refused.
  • TimeoutStopSec should cover the longest unit timeout twice (stop grace plus cgroup drain) for the slowest shutdown wave.
  • SIGTERM stops sahinit gracefully: every service is stopped in reverse dependency order.

Docker (tests and development)

docker run --rm --init --privileged --cgroupns=private ... sahinit supervise --dir /units --socket /run/sahinit/s.sock

The container's root cgroup must be emptied into a leaf first so controllers can be enabled (see internal/cgroup/cgtest). Do not run sahinit as the container's PID 1 (that is init mode); use --init.

Allowing other users to use the socket

sahinit supervise ... --uid 0 --uid 1001 --gid 1001

--uid replaces the default (the supervisor's own uid), so list it too. With another uid the socket is 0660 with group --gid. Every request is still checked by peer credentials, and a request from inside a service is peer_supervised.

First boot as PID 1

Experimental. The host contract: an initramfs (or the kernel) has already made the local root available; sahinit does not discover storage, load modules or configure the network (those are services).

  1. Build a static binary (above) and install it on the root, for example as /sbin/sahinit, with the catalog in /etc/sahinit/units.
  2. Boot with init=/sbin/sahinit (or install it as the initramfs /init). As PID 1 every argument is an init flag; the defaults are --dir /etc/sahinit/units --socket /run/sahinit/control.sock --shutdown-timeout 30s.
  3. Strongly consider --recovery /sbin/your-recovery-program (a local console program run as root). Recovery is off by default: without it a failed strict boot leaves the machine at a console with only the log lines and the power signals.
  4. Verify in a VM first: python3 scripts/test-boot.py.

What PID 1 does, in order: makes / mount propagation private; mounts /proc, /sys, /dev, /dev/pts, /dev/shm, /run and /sys/fs/cgroup where missing; creates a sticky /tmp when missing; opens /dev/console; disables Ctrl-Alt-Del's immediate reboot (it becomes SIGINT); creates /run/sahinit (0700) and /sys/fs/cgroup/sahinit/supervisor; checks for cgroup.kill; enables cpu, memory and pids; starts sahinit supervise --boot-strict ... in /sys/fs/cgroup/sahinit/supervisor with only PATH, HOME=/root and TERM=linux; then reaps every orphan.

In strict boot every boot unit is essential unless it says "essential": false: any refused unit file or limit, a graph error, an essential unit that is not ready when the boot waves end, or one that later becomes failed (a non-zero exit, a signal, restart_limit, watchdog), stops on its own, or waits on a failed needs provider, stops the supervisor, and PID 1 enters recovery. A oneshot that exited 0, a unit in an automatic restart and a unit stopped with ctl stop are fine. Mark units the machine can live without (a getty, a DHCP client) "essential": false; their failure stays theirs, and their dependents wait (blocked). Test a catalog with plain supervise (without --boot-strict) and sahinit validate before booting it.

Persistent ext4 root

contrib/initramfs/init is a BusyBox initramfs /init for a local ext4 root. It, not sahinit, checks the filesystem and switches root: it mounts /proc, /sys and /dev, reads sahinit.root=/dev/DEVICE from the kernel command line (split on whitespace with globbing off, never evaluated), loads virtio_pci, virtio_blk and ext4 if they are modules, waits up to 10 s for the device, runs e2fsck -p (exit 0 or 1 continue; exit 2, errors corrected and a reboot required, syncs and reboot -fs; anything else fails), mounts the root read-write, moves /proc, /sys and /dev, and switch_roots to /sbin/sahinit init with the arguments the kernel passed to /init. On any failure it execs the initramfs's /sahinit init --dir /etc/sahinit/failed (a missing catalog, so strict boot fails and PID 1 waits in recovery); it never opens a shell. Package it with a static BusyBox, /sahinit, e2fsck and its libraries, and the kernel's modules; tests/boot/make-images.sh is a working example. Encrypted, LVM, RAID, UUID-addressed and network roots are not handled.

At shutdown PID 1 runs swapoff on every area in /proc/swaps before unmounting; it never enables swap. python3 scripts/test-boot.py --scenario persistent boots a disposable ext4 image twice and checks it offline with e2fsck -fn after each shutdown.

Console and host services

PID 1 mounts devpts (so /dev/ptmx and /dev/pts/N work) and /dev/shm; it does not start a getty or a login. Every service starts as the leader of a new session (setsid), so a getty can take its terminal as controlling terminal. docs/examples/host/ has example units: a serial agetty (marked "essential": false), udevd with a coldplug udevadm trigger oneshot, modprobe and a foreground udhcpc. They are recipes for an image that already contains those programs, the login and PAM configuration agetty's login needs, udev rules and firmware; adjust paths and interfaces. None uses autologin. sahinit host device-wait --path /dev/vdb is a oneshot that waits for a device node.

Readiness watchdog

A notify unit with "watchdog": "5s" must write a byte to fd 3 at least every 5 s after it is ready; otherwise it is killed (watchdog) and its restart policy applies. For a program that speaks sd_notify, wrap it:

{"name":"agent","type":"simple","ready":"notify","watchdog":"5s","restart":"on-failure",
 "exec":["/sbin/sahinit","host","notify-adapter","--watchdog","5s","--","/usr/sbin/agent"]}

The adapter supports READY=1 and WATCHDOG=1 from its direct child only; run the program in the foreground. This does not replace a hardware watchdog: nothing pets /dev/watchdog.

Power and signals

Signal to PID 1 Effect
SIGTERM or SIGUSR2 power off
SIGINT (also Ctrl-Alt-Del) reboot
SIGUSR1 halt
SIGHUP retry setup and boot, once the supervisor and recovery program are gone

Shutdown: SIGTERM to the supervisor and up to --shutdown-timeout for it to stop every service in reverse order; then SIGTERM and SIGKILL to every remaining process (1 s each); sync; unmount every non-pseudo filesystem, deepest first, remounting busy ones read-only (root last); sync; the power operation. PID 1 never exits, even if the kernel refuses it.

Journal

supervise --log-dir /var/log/sahinit (or init --log-dir ...) keeps a bounded on-disk journal of every unit's stdout and stderr and of lifecycle events; without it output lives only in the in-memory tails of ctl diagnostics. Provision the directory on a writable filesystem:

install -d -o root -g root -m 700 /var/log/sahinit
sahinit logs --unit web --follow
sahinit logs --unit web --contains timeout --since 250
sahinit events --unit web --boot "$(cat /proc/sys/kernel/random/boot_id)"

A directory that cannot be used (read-only root, wrong owner or mode, another supervisor's lock) never fails a boot: the supervisor logs journal_unavailable TOKEN and runs without one. Retention is 1 MiB plus four archives; a full in-memory queue drops records (counted in diagnostics). It is bounded operational logging, not a tamper-evident audit log.

Live catalog changes

sahinit validate --dir /etc/sahinit/candidate
sahinit ctl --socket /run/sahinit/control.sock --dir /etc/sahinit/candidate diff
sahinit ctl --socket /run/sahinit/control.sock --dir /etc/sahinit/candidate apply
sahinit ctl --socket /run/sahinit/control.sock rollback
sahinit ctl --socket /run/sahinit/control.sock explain web

diff, apply, rollback and activate are root only (root_required). apply validates the whole candidate (graph, limits) before it stops anything, stops changed and removed units and every unit that transitively needs one, then starts the affected units that are desired. Unaffected units keep running. A failed replacement restores the old catalog. Side effects of programs (and finished oneshots) are not undone. The change lives in memory only: deploy the files to --dir too, or the next supervisor start loads the old ones. Catalogs with sash units cannot be changed live (catalog_sash). With a deployment, use ctl activate instead.

Sash services

A sash unit runs a sash service script; sahinit verifies a signed grant before every start and performs the script's privileged verbs itself. Set-up, end to end:

  1. Install sash at a root-owned path, for example /usr/bin/sash (the default of --sash). It must pass the executable checks.
  2. Fleet key. Install the fleet's Ed25519 public key (the signer keeps the private key; sahinit never holds it):
    install -o root -g root -m 644 fleet.pub /etc/sahinit/fleet.pub   # 32 raw bytes or 64 hex digits
  3. State directory for floors and the mount table, private to the supervisor's uid:
    install -d -o root -g root -m 700 /var/lib/sahinit/sash
  4. Service account. sash never runs as root: create a user and group, for example app (uid/gid 990). The script's user and group must name them.
  5. Service script and grant, root-owned; the grant exactly 0600:
    install -d -o root -g root -m 755 /etc/sahinit/services /etc/sahinit/grants
install -o root -g root -m 644 app.sash /etc/sahinit/services/app.sash
install -o root -g root -m 600 app.grant /etc/sahinit/grants/app.grant
    The grant (sash/2, purpose service) must name "service":"app" and the same user/group, and list every program the script spawns (exec), every env name (env_names), the file roots (file_read, file_write), mount points and sources (mounts, mount_sources).
  6. Floor (optional but recommended): a signed sahinit-sash-floor/1 document raises the minimum grant serial for the service:
    sahinit sash floor-install --dir /var/lib/sahinit/sash --fleet-pub /etc/sahinit/fleet.pub app.floor
sahinit sash floor-show --dir /var/lib/sahinit/sash --fleet-pub /etc/sahinit/fleet.pub
    Run these as the supervisor's uid (root). Without a floor every serial is admitted.
  7. Unit /etc/sahinit/units/app.json:
    {
  "name": "app",
  "sash": { "file": "/etc/sahinit/services/app.sash", "grant": "/etc/sahinit/grants/app.grant" },
  "execution": { "uid": 990, "gid": 990 },
  "sandbox": { "read_only_paths": ["/usr", "/etc/sahinit/services"], "read_write_paths": ["/srv/app"] }
}
  8. Run with the sash flags (for PID 1, the same flags go to init):
    sahinit supervise --dir /etc/sahinit/units --socket /run/sahinit/sahinit.sock \
  --sash /usr/bin/sash --sash-fleet-pub /etc/sahinit/fleet.pub --sash-floor-dir /var/lib/sahinit/sash
    At start sahinit runs sash --describe for each sash unit (as its uid, sandboxed, 5 s, in a scratch cgroup) and derives ordering, readiness, stop and restart from it. A unit that fails is left out with TOKEN FILE.
  9. Operate: ctl status app shows the grant serial, the entries run and the process name table; ctl reload app and ctl check app run those entries; ctl stop app runs the stop entry, then kills the cgroup and unmounts the service's mounts.

Revoking a grant: install a floor with min_serial above the bad grant's serial. The next start of that service fails with sash_grant_revoked (logged sash_grant app sash_grant_revoked), without restart. A running service is not stopped by a floor; stop and start it.

Rotating the sash fleet key

There is one fleet key. Floors on disk verify only with the key that signed them, and an install compares against the existing floor, so a floor signed by the old key fails closed (sash_floor_store_failed) once the new key is in place. Rotate with the supervisor stopped:

  1. Have the signer issue, with the new key, a grant for every sash service (serial at or above its current floor) and a floor for every service that has one (min_serial at least the current one). Record the current floors: sahinit sash floor-show --dir D --fleet-pub OLD.pub.
  2. Stop the supervisor (under PID 1: boot into recovery or another init).
  3. Move the old floor files out of the state directory (mv D/*.floor /root/old-floors/). Until step 5 there is no floor.
  4. Install the new key at the --sash-fleet-pub path (root, 0644).
  5. Install the new floors: sahinit sash floor-install --dir D --fleet-pub NEW.pub FILE.
  6. Install the new grants (root, 0600).
  7. Start the supervisor; check ctl status.

Because steps 3 to 6 happen with nothing running, no start sees the gap.

Boot policy

Boot policy is metadata only today: these commands verify and store signed documents; the supervisor does not read them. Formats and rules are in boot policy.

install -d -o root -g root -m 700 /var/lib/sahinit-policy
install -o root -g root -m 644 boot-trust.json /etc/sahinit/boot-trust.json
sahinit policy verify --trust /etc/sahinit/boot-trust.json --document policy.json
sahinit policy cache  --trust /etc/sahinit/boot-trust.json --document policy.json --cache /var/lib/sahinit-policy
sahinit policy status --trust /etc/sahinit/boot-trust.json --cache /var/lib/sahinit-policy

never lifetime (the default)

A version-2 policy with "lifetime":"never" has no expiry and needs no clock. It ends only when a higher sequence replaces it or a floor revokes it. To revoke, install a signed sahinit-boot-floor/1 floor:

sahinit policy floor-install --trust T --document floor.json --cache C
sahinit policy floor-show --trust T --cache C
sahinit policy status --trust T --cache C   # a policy below the floor: state revoked, exit 1

Floors only rise (policy_floor_rollback); the same floor again is a no-op; a different floor at the same min_sequence is policy_floor_conflict.

renew lifetime

A renew policy is valid in [not_before, expires_at), in grace until offline_until, then expired. Reading its state needs --trust-system-clock, an explicit assertion that the system clock is trustworthy. Renewal is the optional worker examples/policy-refresh.json:

sahinit policy refresh --trust T --cache C --endpoint https://ISSUER/PATH \
  --credential /var/lib/sahinit-refresh/credential --trust-system-clock

On a never host it prints not_renewing and exits 0 without any network access. Give the unit "restart": "on-failure". There is no issuer yet.

Rotating boot-policy keys

The trust file holds up to 16 keys; each document names its key_id. A cached policy or floor signed by a key that is no longer in the trust file fails verification, which also blocks normal replacement. Rotate with overlap:

  1. Add the new key to keys in the trust file, keeping the old one.
  2. Install a policy signed with the new key at a higher sequence (policy cache; a renew policy also needs --trust-system-clock).
  3. If a floor is installed, install a floor signed with the new key and a higher min_sequence (at most the new policy's sequence). Re-signing the same payload is treated as the same floor and keeps the old file.
  4. policy status and policy floor-show must succeed.
  5. Remove the old key from the trust file; run policy status again.

If the old key was removed too early, put it back, or (an administrator's decision that discards anti-rollback state) remove policy.json and floor.json from the cache and install fresh documents.

Upgrading

  • Under another init: replace the binary atomically (install -m 755 sahinit /usr/local/sbin/sahinit.new && mv ... sahinit), then restart the service. Stopping the supervisor stops every service; the new one cleans leftover service cgroups (cgroup_leftover) and sash mounts (sash_mount_leftover) and boots again. The supervisor re-executes its own binary as the sandbox helper for every launch, so restart it promptly after replacing the file rather than running a new helper under an old supervisor.
  • PID 1: replace the binary and reboot. PID 1 does not re-execute itself.
  • Units: check a new catalog with sahinit validate, then either ctl --dir DIR apply (root, no sash units) or restart the supervisor.
  • State: policy caches, policy floors and sash floors only rise and are read by any version that has them; an upgrade does not touch them.

Rollback

Keep the previous binary (/usr/local/sbin/sahinit.prev). To roll back, move it into place and restart the supervisor (or reboot for PID 1). A rolled-back binary that predates a feature refuses units using it (for example unknown_field for a newer field), so roll the catalog back with it. Floors and the policy cache are not rolled back by design. For PID 1 keep a bootloader entry with the previous init (init=/lib/systemd/systemd, or init=/bin/sh for a shell).

Recovery

When the supervisor exits under PID 1 (a strict-boot failure, a crash), PID 1 kills everything in /sys/fs/cgroup/sahinit, then starts --recovery on the console as root if one is configured (started again shortly after it exits, so it is always available). Repair the catalog from recovery, then send SIGHUP to PID 1 (kill -HUP 1): once the recovery program exits, PID 1 re-runs setup and starts the supervisor again.

  • If the init flags are invalid, PID 1 logs sahinit-init: recovery: setup: ERROR (invalid init configuration, or Go's flag error for an unknown flag) and falls back to the defaults without a recovery program. SIGHUP cannot fix this, because the flags do not change. Reboot with corrected kernel arguments, or with another init.
  • Without a recovery program, PID 1 stays up and answers the power signals and SIGHUP (which retries boot at once).
  • The console log lines start with sahinit-init: (PID 1) or are the supervisor's tokens.

Security model

What sahinit guarantees, what it assumes, and what it does not guarantee. Consolidated from the Threats: notes in the code and the design decisions in hardening, cgroups, sash services 1 and 2, and boot-policy lifetime. Where this page and the code disagree, the code is right and this page is a bug.

Trust assumptions

  • Root and the supervisor's uid are trusted. Everything sahinit reads that decides what runs as whom (unit files, the unit directory, executables and every directory above them, sash scripts and grants, the fleet key, the trust file) must be owned by root or the supervisor's uid and not be writable by anyone else. Anything else is refused rather than trusted.
  • Unit files are untrusted input in shape: strict JSON, closed key sets, no duplicate keys (where encoding/json would silently keep the last), size limits, no symlinks.
  • The kernel is trusted: Landlock, cgroup v2, pidfds, openat2.
  • The disk is not a security boundary against root. Whoever is root can replace the binary, the catalog or the state directories.

Guarantees

What runs is what was checked

  • exec[0], #! interpreters, the sash binary and sash scripts are resolved once with the trusted walk (every directory from / owned by root or the supervisor's uid, not writable by others, sticky directories may be writable by others), so nobody else can swap a component between the check and the exec.
  • On Linux the checked file is executed through its open file descriptor, so the inode checked is the inode run.
  • #!/usr/bin/env and other PATH lookups are refused (exec_interp).
  • A deployment unit's executable is also hashed through that same descriptor on every launch and must match the SHA-256 in the signed manifest (artifact_digest); off Linux, or without a readable descriptor, the launch is refused (verified_exec_unavailable).

A clean start

  • Services never inherit the supervisor's environment; SAHINIT_ names are reserved.
  • Every file descriptor from 3 up is closed at exec except the deliberate ones (the readiness pipe; a script's fd 4; a sash session's fds 3 to 6).
  • An explicit identity always replaces the supplementary groups.

Sandbox (Linux)

  • no_new_privs is always set; a sandboxed unit must run as a non-root uid (sandbox_root), checked at load and again in the helper.
  • Landlock restricts file access to the listed paths, with the rights the kernel's ABI knows; the absence of Landlock, or of a needed right, refuses the start rather than weakening it.
  • Ambient capabilities are cleared.
  • The status claim (no_new_privs,landlock_vN,caps) lists only mechanisms that returned success, and only while a process runs.

The cgroup_trusted boundary

With cgroups, each service is its cgroup: everything it forks starts inside (clone3(CLONE_INTO_CGROUP) or a helper moved in before exec), and when its main process exits for any reason everything left is killed (cgroup.kill) and the service has ended only once the cgroup is empty.

These guarantees hold only for services that cannot write cgroupfs. A unit is cgroup-trusted, and the guarantees are not promised for it, when:

  • it has no sandbox and runs as root or as the supervisor's uid; or
  • its sandbox's read_write_paths include /, /sys, /sys/fs, /sys/fs/cgroup or a path below it; or
  • it keeps dac_override, fowner, chown, setuid or sys_admin.

Such units are allowed, and named (plan prints cgroup_trusted FILE; status has cgroup_trusted: true). A sash unit may never be cgroup-trusted. To bound what a trusted unit can do, sahinit sweeps the root: unknown cgroups are killed and removed (cgroup_stray_cgroup), strangers in its own leaf are killed (cgroup_stray), and processes in the root itself are logged (cgroup_root_member). A trusted service that moves into another service's cgroup cannot be detected.

Limits (memory_max, cpu_max, pids_max) are applied before the process starts; a limit that cannot be applied refuses the unit and is never ignored.

Control socket

  • Local only, one request per connection, 64 KiB frames, strict JSON.
  • The socket is created with its final mode in a private directory and hard-linked into place, so no chmod follows a link; 0600, or 0660 with an explicit group. A stale socket is removed only if it is ours and dead.
  • Peer rules, checked on every request after the frame is read:
    • the peer's uid must be allowed (uid_denied);
    • the peer must not be supervised (peer_supervised): not in any cgroup below the root (a service, the supervisor's leaf, an unknown cgroup), not in a process group a service has led while that group has members, and still the same process that connected (pinned by SO_PEERPIDFD, a pidfd, or its start time);
    • a process in the root itself or in systemd's ROOT/.control is accepted only while a controller is enabled below the root, because the kernel then refuses moves into the root; otherwise sahinit logs cgroup_root_unprotected and refuses them too.
  • diff, apply, rollback and activate additionally need the peer's effective uid to be 0 (root_required), whatever --uid allows: they read a directory as the supervisor and replace what runs.
  • So a service, even one running as an allowed uid, cannot stop or restart other services through the socket.
  • Responses carry tokens, never paths or OS error text.

Signals

On Linux each service's process is signalled through a pidfd, and a process-group signal is sent only while the leader is unreaped; SIGKILL goes through cgroup.kill. With cgroups a reused pid is never signalled; without them, before Linux 6.9, a narrow reuse race remains for the group signal.

sash services

  • sash never runs as root (sash_root), always sandboxed, never cgroup-trusted, so its cgroup holds everything it spawns.
  • The grant is verified by sahinit itself before every start: the fleet key's signature over the exact message, the sash/2 shape, purpose service, no "*", no / root, exp, the service name, the identity, and the serial against the signed floor. sahinit never trusts that sash checked.
  • Every verb sash asks for is re-checked against the grant: programs must be listed and pass the trusted walk; spawned processes run as the unit's own uid and gid under its sandbox; env names must be listed and not denylisted; cwd, probes and file: streams must lie under the grant's roots, opened without following symlinks; signals go only to processes in the service's own name table, never by pid; a check session is read-only.
  • File verbs (mkdir, chown, chmod, touch, ln, rm) run as root after the checks, with openat2(RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS) from the root, on a single final name, never by path. Hard links are refused; only targets the service already owns are changed; owners are only the service's own identity; modes never include setuid or setgid; creation runs with the service's filesystem uid and gid, so a rename race cannot make a root-owned file the service's.
  • Mounts: types tmpfs, proc, sysfs, devpts, or binds from listed sources; always nosuid,nodev; no overlay or other options; the mount point must be listed and may not be at, under or above a writable root; each mount is tracked by its unique mount ID so umount and remount act only on sahinit's own mount.
  • Secret env values reach only the child's environment; spawned children never dump core.
  • Floors only rise, are signed under their own domain (no grant or policy verifies as a floor), and fail closed when unreadable or unverifiable.

Deployments

A generation is staged only when its policy verifies under the local trust, the manifest's exact bytes match the signed catalog_sha256, every unit and artifact matches its manifest digest, and the unit set and needs match the policy; it is re-verified on every load. Each start (manual, boot, restart, dependency resume) is admitted against the active generation's policy and the revocation floor (policy_revoked): grace admits only offline_units, an expired policy only automatic restarts of runtime_restart_units. apply and rollback are refused in this mode; earlier content returns only as a newly signed, higher-sequence generation. This binds the declared files, not the kernel, shared libraries, an interpreter's dependencies or files named in arguments.

Boot-policy metadata

Ed25519 over a domain-separated message and the exact payload bytes; strict schema with no unknown, missing or duplicate fields; host and recovery binding; local ceilings; renewal ordering (no lower sequence, no silent change at the same sequence or generation); a monotonic revocation floor; atomic, fsynced installs under a lock; corrupt state fails closed. The renewal client uses TLS 1.3 only, the system roots, no proxy, no redirects, bounded sizes and times, and a credential that is never printed.

What is NOT guaranteed

  • Boot policy is not enforced for --dir catalogs. Only a deployment (--deployment-root) admits units by policy. Boot jobs and their script hashes are refused (deployment_jobs); nothing runs them. There is no policy issuer and no artifact downloader.
  • Root on the host can defeat everything here: replace the binary, edit the catalog, delete or restore the policy cache and the floors (the anti-rollback guarantee is file-based; there is no TPM or verified boot).
  • Cgroup-trusted units (above) can leave their cgroup or kill sahinit.
  • Without cgroups (--no-cgroups, or not Linux), a service that calls setsid escapes kill-all and the peer check, and there are no limits.
  • Network access is not confined by the sandbox.
  • Capabilities: a sandboxed unit cannot be given a capability today (sandbox_cap); a sash spawn cannot either (caps_unsupported).
  • Peer pinning before Linux 6.5 leaves a narrow pid-reuse window between connect and accept.
  • The grant's host is not checked: sahinit has no host name.
  • A legitimate mount is visible host-wide: mounts are made in sahinit's own mount namespace.
  • Output tails, events and the journal are not an audit log: tails are in memory and lost on exit; the journal (--log-dir) is bounded, drops records when its queue is full, may lose its unsynced tail on power loss, and is not tamper-evident. Both contain whatever the service printed, secrets included; journal files are 0600 to the supervisor's uid.
  • Live catalog changes cannot undo side effects: a failed apply restores the old catalog's configuration and processes, not what the programs did.
  • The service watchdog is not a hardware watchdog: a hung kernel or PID 1 is not reset.
  • --trust-system-clock is an assertion, not authentication: time is never established from a policy or from disk.
  • The recovery program runs as root on the console with no authentication added by sahinit; provision an authenticated one.
  • PID 1 mode is experimental: storage discovery beyond sahinit.root=/dev/... and a hardware watchdog are not provided; the filesystem check and switch-root are done by the separate initramfs script (contrib/initramfs/init), proven only on a disposable ext4 disk in QEMU.
  • Old-kernel fallbacks (no close_range, older Landlock ABIs, no cgroup.kill, no clone3 into a cgroup) are tested only through hooks, not on real kernels.

Reporting

Report a way past any of these rules privately to the maintainers rather than in a public issue.
