Single-file performance

Measurements and implementation notes, 2026-10-22. These are local results, not a claim to outperform every transport or an independent security audit. One grant still transfers one regular file. The v1 wire layout is unchanged.

Implemented

  • Actionable overdue timers run immediately, including the QUIC datagram runner. Inactive feedback and cleared NACKs cannot create a busy loop.
  • pace-bbr tolerates up to 2 ms of scheduling lateness. The previous 1 ms cutoff discarded credit on roughly 1 ms Linux timer wakeups plus overhead. Longer idle gaps reset credit; catch-up remains bounded by pacing and the flight window. QUIC still disables this controller.
  • The flight window accounts for observed delivery-feedback spacing over ten samples, capped at 50 ms. This allowance expires, ignores replayed delivery counts, and never bypasses the loss cap or PROBE_RTT.
  • New source data uses 256 KiB read-ahead. Pending frames own their bytes; repairs reread the file and receive fresh sequence numbers. The original source hash validation is retained.
  • In-order DATA is hashed from authenticated plaintext only after a full successful write. Overlaps retain first-write-wins. Out-of-order bytes and ZERO ranges still fold from the temp file when contiguous.
  • Decryption scratch space is reused and cleared on peer close. Failed opens expose no plaintext to the writer. Cipher and route-token comparison rules are unchanged.
  • The common one-hole prefix update and missing-range visitor avoid repeated interval allocations. Short reads and writes fail closed.
  • --diag reports sender pacing state, bandwidth estimate, flight bytes, window cap, delivered prefix, and RTT at most once per second. No credentials, grant material, or file contents enter these diagnostics.

Reproduce

go test ./...
go test -race ./...
go vet ./...
go test ./internal/engine -run '^$' -bench BenchmarkFile -benchmem -count=3
go test ./internal/udp -run '^$' -bench BenchmarkDiskTransfer -benchtime=1x -count=3
go test ./internal/udp -run '^TestLoopbackThroughput30MB$' -count=3 -v

Run benchmarks without concurrent compiles or other load. Record OS, CPU, Go version, granted socket buffers, filesystem, and whether caches are warm. Do not compare a memory-file loopback result with a disk-transfer result.

The file microbenchmarks use 4 MiB of nonzero data on actual files. They isolate source classification and receiver writes/hashing, excluding network, AEAD, preparation, and durable commit. On Darwin amd64, Intel i9-9880H, Go 1.27, three samples before and after the I/O changes:

Measurement Before After
Source classification 814–845 MB/s 3,273–3,369 MB/s
Receiver writes and hash 190–214 MB/s 273–282 MB/s
Receiver allocations per 4 MiB 3,651 9

The baseline is commit 56d69c7 with the same benchmark code. These are warm-cache results. Source buffering adds bounded memory and does not yet remove the allocation of each outgoing plaintext and ciphertext frame.

BenchmarkDiskTransfer moves 30 MB through actual source and destination files over loopback UDP. Timing includes both source hash passes, encryption, transfer, destination fsync, and rename. Source creation and independent byte-for-byte destination verification are outside the timer. It does not contact SystemAPI or measure a cold disk. The original-code baseline measured 24.3–40.6 MB/s; the first optimized runs measured 43.9–54.9 MB/s. Host load varied, so these ranges are evidence of improvement, not a precise speedup. After the final pacing changes and completion of the test suites, three additional runs measured 55.0, 55.2, and 55.2 MB/s (0.543–0.545 s each).

Linux container loopback with memory-backed files timed out at 16 s in three consecutive runs before correcting pacing slack. Diagnostics showed bandwidth near 2 MB/s and flight bytes below the window cap. After the 2 ms correction, three runs completed in 0.271–0.384 s, or 78–111 MB/s. That test excludes source preparation and durable file commit; it is a scheduling regression check.

Allocation overhaul (2026-10-22)

UDP now opts into a per-peer cache of at most 64 returned datagram buffers. New buffers use 1,232-byte or 8,192-byte size classes; retained buffer capacity is at most 512 KiB, excluding outstanding packets and other engine storage. Only after a synchronous send finishes or fails does a batch return to the cache. Queued pre-pin packets remain owned until sent or discarded. Returned buffers are wiped, including the header route token. Existing allocating Take callers and QUIC retain their previous ownership contract.

SealInto writes into caller-owned storage without overlapping AEAD output with additional data. Sessions reuse separate send/open nonce scratch under single-owner execution; nonce bytes remain direction plus sequence. UDP compares binary IP/port/zone values rather than formatting peer addresses per packet.

The focused seal/open test measures zero allocations after setup with supplied buffers. This is not a claim of a zero-allocation transfer: outgoing plaintext, socket address decoding, and other work still allocate.

An isolated archive of baseline 9db1211 and the final implementation ran five 30 MB disk/UDP samples each on Darwin amd64, Intel i9-9880H, Go 1.27.3. Source pipeline was off. Both include source preparation and durable commit, use warm caches, and independently verify destination contents. No test or compile jobs from this session ran concurrently with the timed samples.

Measurement Baseline median Final median
Allocations per transfer 396,150 125,908
Bytes allocated per transfer 72,762,696 36,200,040
Goodput 56.21 MB/s 57.78 MB/s

Allocation count fell about 68%, and allocation volume about 50%. Allocated bytes are cumulative allocations across both peers, not peak RSS. The local median goodput difference is about 3%; five short sequential samples do not establish a general throughput advantage. Earlier intermediate versions/runs varied from 49.49 to 59.68 MB/s. Allocation reduction is the primary evidence.

Baseline goodput samples: 53.24, 57.30, 56.97, 54.14, 56.21 MB/s. Final goodput samples: 57.78, 56.32, 57.93, 57.36, 57.86 MB/s. Final allocation counts: 120021, 133647, 125908, 121614, 126906. Reproduce with go test ./internal/udp -run '^$' -bench 'BenchmarkDiskTransfer/pipeline=false' -benchtime=1x -count=5.

Validation: full Darwin and Linux suites passed; full Darwin race suite passed before the final size-class/AEAD-slice refinements, followed by targeted race checks and full Darwin tests, and Linux regression checks for those refinements. go vet ./... passed. New tests cover independent reference nonce/wire encoding, tampered tags in reused storage, zero-allocation seal/open scratch, outstanding batch ownership, cache bounds/wiping, size-class transitions, IPv4-mapped peer identity, port/host changes, and distinct IPv6 zones. Existing fail-closed grant, path, replay, hash, and peer-pinning suites remain in force.

Remaining work

Source read-ahead experiment (2026-10-22)

put --pipeline-source enables one asynchronous source reader. It hands off owned buffers through bounded channels; the engine retains hashing, sealing, sequence allocation, and pacing. Two source buffers total at most 512 KiB. Repairs reread the source, ZERO scans remain synchronous, and receiver writes and commit are unchanged. Initial source validation still precedes the transfer. The option is off by default and requires no negotiation or wire changes.

Final measurements on Darwin amd64, Intel i9-9880H, Go 1.27.3, with warm file caches and no concurrent test/compile jobs from this session:

Measurement Pipeline off Pipeline on
4 MiB source classification, three samples 3,067–3,281 MB/s 3,071–3,188 MB/s
30 MB disk/UDP transfer, five samples 52.07–54.82 MB/s 53.19–55.05 MB/s
Disk/UDP median 53.59 MB/s 53.96 MB/s
Source microbenchmark allocation bytes per iteration 4,456,461 (representative) 4,719,160 (representative)

The median difference is below 1%, with overlapping ranges. This does not establish an end-to-end performance improvement on this workload. Keep the option experimental; test cold or slower storage and larger transfers before considering a default change. Allocation bytes include per-frame allocations over the whole iteration, not just the bounded live lookahead buffers. Earlier samples taken concurrently with tests were excluded from this table.

Reproduce with the existing BenchmarkFileSource and BenchmarkDiskTransfer: both now report pipeline=false and pipeline=true subbenchmarks. Use -benchtime=1x -count=5 for the disk benchmark. Each disk sample independently verifies the destination after durable commit.

Validation: full Darwin and Linux-container suites passed; Darwin engine and CLI race suites and go vet ./... passed. New tests cover concurrent read-ahead, worker join and buffer wiping, skipped blocks, direct repair reads, pending frame ownership, internet/DC block boundaries, partial tails, short/error reads, abort without commit, loss repair, ZERO runs, and the CLI option. This phase does not implement concurrent destination writes or a worker pool for crypto. Close waits for any outstanding filesystem read; no cancellation latency bound is claimed for a blocked filesystem.

Next measurements

  1. Measure sustained transfers between physical Linux hosts at multiple RTTs, with random loss, burst loss, reordering, reverse-path outages, competing flows, and slow storage. Existing deterministic path tests remain required.
  2. Separate selectively delivered byte credit from contiguous completion. Today a missing prefix still keeps later segments in flight. ZERO and retransmission accounting need a specified, tested design before changing it.
  3. Consolidate duplicated source validation without weakening change detection or allowing preparation to consume the grant's first-packet deadline.
  4. Reduce outgoing allocations and improve effective send batches. Any buffer pool needs explicit ownership until socket completion and failure tests.
  5. Evaluate batched destination writes, kernel pacing, and a real Linux io_uring backend using profiles. No io_uring implementation is claimed here.

Retain TLS 1.3, ChaCha20-Poly1305, authenticated grants, path confinement, first-write-wins, hash verification, and durable commit throughout. Compression, MTU negotiation, resume, and wire-format changes require separate specifications.

Validation

The final implementation passed go test ./... on Darwin amd64 (Go 1.27.3) and in the local Linux golang:1.27 container, plus go test -race ./... and go vet ./... on Darwin. The existing suites cover tampered packets, expiry, grant binding and purpose, path escape and symlinks, hash mismatch, replay, and peer pinning. Added tests cover overdue and inactive timers, repair recheck timing, first-send credit, 1.1 ms scheduling lateness, bounded and aging feedback allowance, overlapping writes, short I/O, source-buffer ownership, scratch clearing, and a bitmap reference check of hole tracking.

These checks do not establish Internet fairness, production host isolation, or performance at 10/25/100 Gbit/s. Those remain deployment and evaluation work.

Measurement tranches (2026-10-22)

The disk benchmark now reports preparation, AttachSource validation, setup, transfer/verification, durable commit, and close separately. A new opt-in BenchmarkSustainedTransfer covers both payload profiles and source-pipeline settings with streamed random fixtures and bounded-memory verification. scripts/profile-transfer.sh collects unprofiled timing separately from CPU, allocation, and execution-trace artifacts. See the lab guide for precise timing boundaries, reproduction, and the pending physical-host plan. No source hash pass or production transport behavior was removed.

Three 256 MiB warm-cache Darwin samples per case measured median end-to-end 65.56 MB/s (internet, pipeline off), 65.49 MB/s (internet, on), 95.71 MB/s (DC, off), and 94.54 MB/s (DC, on). Single 2 GiB runs with pipeline off measured 63.59 and 101.57 MB/s respectively; their transfer-only intervals measured 91.59 and 199.0 MB/s. Two initial hash passes consumed about 10.3 s per 2 GiB run. These are observations on loopback, not physical-host or competitor results. The new random fixture differs from the older benchmark's deterministic body. Raw timing and profile reports are in docs/benchmarks/2026-10-22-transfer/; the research brief interprets the findings and defines FTP/SFTP/SCP comparisons and the proposed agent-facing product contract.
